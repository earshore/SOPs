## 一、修复项清单

### F1｜P0-1a：AI 智能分析「证据深度」下拉去掉耗时展示

- **文件**：`src/modules/app_center/views/master_analysis/ai_analysis/components/AlpinePanel.ts`
- **现状**：`evidenceDepthOptions`（L1006-1032）label = `快速 · 推理低 · 预计 22-36 秒`，时间来自 `estimateRunAtDepth`。
- **变更**：
  1. label 改为 `快速 · 推理低`（仅档位 + 推理等级）。
  2. 删除 `estimateText` 组装与 `estimateRunAtDepth` 调用，统一用 `resolveAnalysisReasoningPrefs(userPrefs, depth)` 计算 `reasoningLabel`（与 `estimateRunAtDepth` 内部同一函数，推理等级联动不变）。
  3. 清理孤儿 import：`estimateRunAtDepth`、`mergeProducts`、`getProductsByAsins`（仅此处使用则移除；`Product` 类型若仅用于 estimateRunAtDepth 形参也一并清理）。
  4. 更新 getter 注释（耗时估算改为 toast 同源口径）。
- **验收**：下拉选项不出现任何"预计/秒/分钟"字样；推理等级联动显示不变。

### F2｜P0-1b：耗时估算基准校准 + 新增单调用估算导出

- **文件**：`src/modules/app_center/views/master_analysis/ai_analysis/services/analysisTimeEstimator.ts`
- **现状**：`PER_CALL_SECONDS`（off=6, low=12, medium=25, high=45, xhigh=70, max=100），注释自称"实测校准"但明显过期（Deep Chat 单次调用实测 ~20s，快速档多目标实测 128s vs 预估 22-36s）。
- **变更**：
  1. 上修基准（保守校准，约 2.2x）：`off 6→14, low 12→26, medium 25→55, high 45→100, xhigh 70→150, max 100→220`，注释写明校准依据与"保守估算"定位。
  2. 新增导出 `estimateSingleCallTime(reasoning: AnalysisReasoningPrefs, options?: { toolScale?: boolean }): AnalysisTimeEstimate`：
     - 单次调用 = `perCallSeconds × 1.15`；`toolScale` 时再 × 2.2（大 prompt 工具场景，基于 Keyword Hunter 实测 ~60s 回归）。
     - 区间复用 0.8/1.3 口径与 `formatDurationLabel`。
- **验收**：`estimateAnalysisTime` 行为不变（仅基准值变化）；单调用估算输出合法区间；既有测试全部通过（测试均为相对断言，无硬编码秒数）。

### F3｜P0-2：Listing 评审页（Keyword Hunter）去硬编码时间 + 启动 toast 测算

- **文件**：`src/modules/app_center/views/keyword_hunter/analysis/index.ts`
- **现状**：
  1. `showLoadingState` L582 硬编码「这可能需要 10 ~ 30 秒，请耐心等待」。
  2. `runLLMAnalysis` 仅 bypassCache 且已有报告时弹「正在重新生成评审报告…」，无时间测算；autoStart（SEO「进入分析」）路径无任何 toast。
- **变更**：
  1. loading 文案改为「正在生成评审报告，请稍候…」（不承诺时间）。
  2. `runLLMAnalysis` 确认后、`attachAnalysisRunToPage(startAnalysisRun(...))` 前，统一弹启动 toast：
     `正在生成评审报告 · 预计 ${estimateSingleCallTime({ enabled: false, effort: 'off' }, { toolScale: true }).label}`
     - 覆盖手动（重新生成）与 autoStart（SEO 进入分析）两条路径；原「正在重新生成评审报告…」分支合并进新 toast（无独立保留价值）。
     - 等效 off 档依据：KH 经 `callLLM` 调用不携带 effort 参数，实际走 provider 默认。
  3. import `estimateSingleCallTime`（相对路径 `../../master_analysis/ai_analysis/services/analysisTimeEstimator`，同 app_center 域）。
- **验收**：评审页加载态无"10 ~ 30 秒"字样；点「重新生成」与 SEO「进入分析」均弹含预计区间的 toast。

### F4｜P1a：设置健康消息去重收敛（存储警告归 quota bar）

- **文件**：`src/components/settings/domain/settingsHealth.ts`
- **现状**：`evaluateSettingsHealth` 把「本机存储占用较高」与 LLM 配置缺失消息平铺进 `healthMessages`，设置页脚与 quota 警告条**同屏重复显示**同一信息。
- **变更**：storage 警告不再产出到 healthMessages（quota bar `quotaWarningVisible` 独立驱动，已存在）；保留 `storageUsageRatio` 参数（调用方不动），注释说明归属。剩余消息顺序天然 error 优先（LLM 缺失在前、runtime 修复提示在后）。
- **验收**：设置页脚不再显示存储警告；quota bar 仍显示；无设置健康相关测试受影响。

### F5｜P1b：AI 分析启动 toast 精简

- **文件**：`src/modules/app_center/views/master_analysis/ai_analysis/components/actions.ts`
- **现状**：`prepareAnalysisRun` toast 堆叠「· 约 N 次分片调用 · 证据清洗约 N 条 · 缓存命中 n/m 维」，信息过载。
- **变更**：toast 精简为 `正在分析 N 个 ASIN · 快速档 · 推理低 · 预计 X-Y 秒` +（有缓存时）` · 缓存命中 n/m`；删除 mapCalls/hygienePart 及 `estimateAnalysisWorkload` 调用与 import（orphan 清理）。
- **验收**：开始分析 toast 信息收敛，预计时间保留（P0 要求）。

### F6｜P2：Keyword Hunter 完成态统一（单一状态源）

- **文件**：`src/modules/app_center/views/keyword_hunter/analysis/index.ts`
- **现状**：`renderAnalysisSuccess`（L144-161）先 `setBtnState('success','报告已生成')` 后又把按钮文本改回「重新生成」——状态类与文案矛盾；完成态由按钮/文本/报告存在性多处推导。
- **变更**：`renderAnalysisSuccess` 中按钮处理统一改为 `updateAnalyzeButtonState()`（该函数已以 `activeAnalysisRun.status + hasContent + hasReport` 为单一派生源）；删除双写逻辑。
- **验收**：分析完成后按钮为 success 样式 + 「重新生成」文案（可再次触发），与 `updateAnalyzeButtonState` 口径一致。

### F7｜P3：网络分区搜索标签可辨识

- **文件**：`src/components/settings/domain/settingsSearch.ts`
- **现状**：`SECTION_LABEL_BY_ID['settings-section-network'] = '工具策略'`（与工具策略分区同名，搜索"网络"命中时显示误导）。
