## 🔧 测试编写指南

### 测试文件命名
```
tests/
├── unit/              # 单元测试
│   └── [模块名].test.ts
├── integration/       # 集成测试
│   └── [功能名].test.ts
└── e2e/              # E2E测试(未来)
    └── [流程名].test.ts
```

### 测试结构模板
```typescript
import { describe, it, expect, beforeEach, afterEach, vi } from 'vitest';
import { YourModule } from '@/path/to/module';

describe('YourModule', () => {
    beforeEach(() => {
        // 准备工作
    });

    afterEach(() => {
        // 清理工作
    });

    describe('功能分组1', () => {
        it('应该做某事', () => {
            // Arrange
            const input = 'test';
            
            // Act
            const result = YourModule.doSomething(input);
            
            // Assert
            expect(result).toBe('expected');
        });
    });

    describe('错误处理', () => {
        it('应该处理错误情况', () => {
            expect(() => {
                YourModule.throwError();
            }).toThrow('Expected error');
        });
    });

    describe('边界条件', () => {
        it('应该处理空值', () => {
            expect(YourModule.handle(null)).toBeNull();
        });
    });
});
```

### 测试覆盖要求
每个模块测试应包含:
1. ✅ 核心功能测试(Happy Path)
2. ✅ 错误处理测试
3. ✅ 边界条件测试
4. ✅ 异步操作测试(如适用)
5. ✅ Mock和Spy测试(如适用)

## 🚨 风险和缓解

### 风险1: API不匹配
**影响**: 测试编写困难,需要反复修改  
**缓解**: 
- 先阅读源代码了解API
- 创建简单测试验证API
- 遇到问题及时调整

### 风险2: 时间不足
**影响**: 无法达到80%覆盖率目标  
**缓解**:
- 优先测试P0模块
- 降低P2模块测试深度
- 可接受75%覆盖率

### 风险3: 测试维护成本
**影响**: 测试频繁失败,维护困难  
**缓解**:
- 编写稳定的测试
- 避免测试实现细节
- 使用测试工具函数
